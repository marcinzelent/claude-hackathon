## Problem Statement
- **Audience:** job seekers (career changers, newcomers to Berlin, recent grads) who go to networking events to find their next role.
- **Their problem with AI today:** they know AI exists, but don't use it for the hardest part of job hunting: walking up to a stranger at an event. They spend the evening with whoever is standing nearest and leave without the one conversation that mattered.
- **What the demo lets them do:** open tonight's event, paste their own profile and what they're looking for, and get a ranked list of the attendees worth meeting, each with why, an icebreaker, and one follow-up question. A "Do it yourself" panel hands them a reusable prompt so they can repeat the method in Claude.ai for any event.

## What Makes This Cool
- Existing AI-matchmaking (KonfHub Gold plan, inEvent) is organizer-side: it only exists if the organizer pays and switches it on. This is **attendee-side**: the job seeker brings their own wingman.
- Icebreakers are specific to the other person ("You moved from logistics to product at X, how did you pitch that switch?"), not generic "What brings you here?".
- It works on a phone as an installed PWA, and the last results stay available offline, which matters in a basement venue with bad wifi.

## Two data paths: product vs. demo
- **Product path (any event, attendee side):** the user pastes the attendee notes they can see (names + headlines from a public Luma page, a speaker list, an organizer's list) into a text box. Claude matches against that. This is supported in the demo app as the "Paste attendees" tab and is the honest answer to "how does a real attendee get the list?".
- **Demo path (rich data):** a Luma event the team hosts, with teammates as consenting guests. Because the team is the host, the guest list is exportable; LinkedIn profiles are enriched once via Apify. The README and the video say plainly that the hosted event is a demo stand-in for the real event the user attends.

## Constraints
- Hard deadline 16:00; feature freeze 15:00; video at 15:00. Started design at 12:32, about one hour behind the plan.
- Event rule: "No real personal data. Use fake or sample data." GDPR in Berlin.
- Luma's official MCP (mcp.luma.com) is read-only, OAuth sign-in, and its guest tools only cover **events you manage** (source: help.luma.com/p/mcp).
- Apify "no cookie" LinkedIn actors are community-maintained (~3.0 ratings, some "under maintenance"), $1–9 per 1k profiles, and live runs take 30–120 s.
- **LinkedIn's terms prohibit automated scraping**, even when the profile owners consent. The team accepts this risk for the demo only: Apify runs offline, once, on the 5 consenting teammates' URLs; the public repo ships no scraped data, and the app never scrapes a URL typed in by a user.
- Secrets only in `.env` (`ANTHROPIC_API_KEY`, optional `APIFY_TOKEN`; both listed in `.env.example`).

## Premises (agreed)
1. Audience and the "use AI for networking" angle are as stated above.
2. The team creates its own Luma event and registers as its guests, so the team is the host and every attendee consented. **Before recording the video, the team checks with an organizer that consenting teammates' own profiles are OK under the "no real personal data" rule, and notes the answer in the README.** If the organizer says no, the demo runs on `data/sample_profiles.json` (fake people) with no other change.
3. The Luma event has a **required registration question: "Your LinkedIn URL"**, so each guest maps to exactly one profile without name-guessing.
4. Apify scrapes only URLs present in `data/event.json`. The user's own profile is **pasted text** (LinkedIn About + Experience), never a URL scrape.
5. Claude is the product core: rank, explain, write icebreakers.
6. PWA = one HTML page + manifest + small service worker. No framework.

## Recommended Approach
**A: Sync once, demo live.** Python (FastAPI) backend that holds the keys, static PWA frontend. Only Claude runs live during the demo.

```
 OFFLINE, once, before the demo
 Luma host dashboard ── CSV export ──► scripts/import_luma.py ──► data/event.json
   fallback 1: Claude Code + Luma MCP writes the same JSON          {event, guests[{id, name, linkedin_url}]}
   fallback 2: hand-written data/event.json (5 entries)
 scripts/enrich.py ── Apify run-sync on URLs in event.json ──► data/profiles.json (git-ignored)
   (warm-up command; re-runnable; 180 s timeout per run)

 LIVE, during the demo
 PWA (public/)                                  server.py (FastAPI)
 ┌──────────────────────────────────┐   POST    ┌───────────────────────────────────────┐
 │ 1. Me: pick "I am <guest>" from  │ /api/match│ load event.json + profiles.json        │
 │    the list (or "not on list"),  │─────────► │ (or sample_profiles.json, see below);  │
 │    paste About text, "tonight I  │           │ drop the user's own guest id;          │
 │    want..."                      │           │ Claude: prompts/match.md → JSON        │

 │    event, free text)             │ ◄──────── │ returns ONLY Claude's output, never    │
 │ 2. Event card                    │           │ raw profiles                           │
 │ 3. Ranked cards: why ·           │           └───────────────────────────────────────┘
 │    icebreaker · follow-up · Met ✓│

   sw.js caches the static shell only. app.js saves the last /api/match result in
   localStorage and renders it when offline (Cache API can't key POST requests).
```

Behavior details:
- **Self-exclusion:** the "I am <guest>" picker sends the user's guest id; the server removes it from the candidates before calling Claude. Result count is `min(3, candidates)`; with 4 teammates as candidates the ranking is "top 3 of 4". If time allows, add 6–8 fake sample guests (marked "sample") to make ranking meaningful.
- **Sample fallback:** if `data/profiles.json` is missing (enrich never ran or failed), the server uses `data/sample_profiles.json`, a separate, committed list of **fake** people with fake names, never fake profiles under real teammates' names. The UI shows a visible "Sample data" badge on the event card whenever this path is used.
- **Claude output:** `[{name, fit (1–10, how well this person matches the user's goal), why, icebreaker, follow_up}]` via structured JSON output. The prompt tells Claude to cite only facts present in the supplied profile text and to say "not enough info" instead of inventing facts. If the user's pasted profile is under ~2 sentences, Claude still returns matches and adds one `tip` string suggesting what to add.
- **Model:** one constant `MODEL` in `server.py`; the builder confirms the exact current id on docs.claude.com before the first call (Sonnet-class for speed).
- **Met ✓:** localStorage-only check mark per person, persists across reloads and offline, no server effect, no re-ranking.
- **"Do it yourself" panel** (the AI-education element): (a) a copyable prompt template with three placeholders: `[MY PROFILE]`, `[WHAT I WANT TONIGHT]`, `[ATTENDEE NOTES]`; (b) three short steps on gathering attendee notes by hand (event page guest list, speaker list, ask the organizer); (c) an "Open Claude.ai" link. It's the same prompt as `prompts/match.md`, with placeholders instead of data.
- **Errors:** friendly message on Claude failure ("Couldn't reach the AI, try again"); the last cached result stays visible.
- **Exposure:** local only, plus a temporary cloudflared tunnel during video recording (shut down after). No endpoint returns raw profile data. No passcode needed if the tunnel is temporary.

Files (split so teammates don't collide):
- `server.py`: FastAPI, `/api/event` (names + headlines only), `/api/match`, serves `public/`.
- `prompts/match.md`: the matching prompt (product/design person tunes it).
- `scripts/import_luma.py`, `scripts/enrich.py`: offline import + warm-up.
- `public/index.html`, `public/app.js`, `public/style.css`, `public/manifest.webmanifest`, `public/sw.js`, `public/icon-*.png`.
- `data/sample_profiles.json` (committed, fake), `data/event.json` + `data/profiles.json` (git-ignored, real teammates).
